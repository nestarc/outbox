## 1. Summary

`@nestarc/outbox` v0.1.0 already solves the core transactional outbox problem for NestJS + Prisma: store an event row in the same database transaction as business data, then deliver it asynchronously through a poller.

v0.2.0 should move the package from a working local-handler MVP to an operational reliability layer. The release should focus on the pieces required before users can safely use it for external broker publishing and production recovery:

1. Fix the transport model so broker publishers do not require local handlers.
2. Add admin/DLQ operations for failed and pending events.
3. Introduce a stable event envelope and metadata fields for broker keys, idempotency, ordering, tracing, and tenancy.
4. Add optional Postgres `LISTEN/NOTIFY` wakeup with polling fallback.
5. Add tenant propagation and observability hooks if they fit the release budget.

The release should not try to become a full event platform. Full inbox processing, dashboard UI, logical replication, multi-ORM support, and first-party adapter packages for every broker should stay out of 0.2.0.

## 2. Product Positioning

### 2.1 One-line definition

Prisma-native transactional outbox for NestJS that stores committed domain events in PostgreSQL and reliably relays them with retries, recovery, and production operations.

### 2.2 Nestarc position

`outbox` is a **reliability / infrastructure layer** in the nestarc ecosystem.

It should become the common event spine for:

- `@nestarc/tenancy`: tenant-aware event persistence and handler execution.
- `@nestarc/idempotency`: duplicate-safe consumer and replay patterns.
- `@nestarc/jobs`: converting committed domain events into background jobs.
- `@nestarc/webhook`: feeding reliable outbound webhook delivery.
- `@nestarc/audit-log`, `@nestarc/soft-delete`, `@nestarc/data-subject`: compliance and lifecycle event fan-out.

### 2.3 Differentiation

The strongest 0.2.0 positioning is:

> Published Prisma-native NestJS outbox with schema-free SQL migration, Postgres wakeups, and production broker-ready delivery.

This is narrower and safer than claiming there are no Prisma competitors. Research found packages that claim Prisma support, but `@nestarc/outbox` can still differentiate by staying small, NestJS-native, schema-free from the Prisma user's perspective, and aligned with nestarc SaaS modules.

## 3. Goals and Non-goals

### 3.1 Goals

- Make custom broker publishing a first-class supported mode.
- Preserve 0.1.0 local handler behavior where possible.
- Give operators a public API for inspecting, retrying, and cleaning up outbox rows.
- Add metadata needed for idempotency, broker routing, tracing, tenancy, and ordering.
- Keep PostgreSQL polling as the durable source of truth.
- Add low-latency wakeup without depending on CDC infrastructure.
- Keep the package usable with NestJS 10/11, Prisma 5/6, and Node 20+.
- Keep v0.2.0 a focused minor release with additive migrations and low dependency growth.

### 3.2 Non-goals

- No full inbox module in 0.2.0.
- No dashboard UI.
- No logical replication or WAL tailing implementation.
- No multi-ORM support.
- No required Kafka, RabbitMQ, NATS, SQS, Redis, or Temporal dependency.
- No claim of exactly-once end-to-end delivery.
- No strict aggregate-level FIFO guarantee unless a later implementation plan proves it is small enough.
- No bundled OpenTelemetry package in core; provide hooks first.

## 4. Current State

### 4.1 Implemented in 0.1.0

- `OutboxModule.forRoot()` and `forRootAsync()`.
- `OutboxEmitter.emit(tx, event)` and `emitMany(tx, events)`.
- `OutboxEvent` base class with runtime `eventType` validation.
- `@OnOutboxEvent()` decorator.
- `OutboxExplorer` handler discovery through NestJS `DiscoveryService`.
- `LocalTransport` that invokes in-process handlers sequentially.
- `OutboxPoller` with polling, `FOR UPDATE SKIP LOCKED`, retry/backoff, stuck event recovery, and graceful shutdown.
- Raw SQL migration for `outbox_events`.
- Unit tests and PostgreSQL E2E tests.

### 4.2 Known gaps

- Custom broker transport is configurable, but no-handler events are failed before transport dispatch.
- `OutboxTransport.dispatch(record, handlers)` mixes two delivery models:
  - local handler invocation needs handlers;
  - external broker publishing does not.
- Failed events can only be manually reprocessed by SQL.
- Event rows do not have metadata fields for aggregate id, partition key, headers, correlation id, or idempotency key.
- `tenant_id` exists in the table but is never written.
- Local handlers receive only `payload`; they do not receive event id, retry count, tenant id, or correlation metadata.
- `emitMany()` loops and inserts one event at a time.
- Multi-instance duplicate prevention is documented but not covered by a dedicated E2E test.
- `OutboxPoller` owns scheduling, repository access, retry policy, recovery, dispatch, and shutdown, so v0.2.0 changes should avoid increasing that coupling where possible.

### 5.1 Backend lead

0.2.0 must ensure broker publishing works without fake local handlers.

### 5.2 Platform/on-call engineer

The user needs to inspect stuck, failed, and pending rows, retry failed events, and know whether the backlog is healthy.

The user needs event ids, idempotency keys, aggregate ids, partition keys, and trace metadata for duplicate handling and broker routing.

0.2.0 must add a stable envelope before adding official broker adapters.

## 6. Proposed Scope

### 6.1 P0 - Broker-capable transport mode

#### Problem

The README shows a Kafka-style custom transport, but current poller behavior fails an event if no local handler is registered. That makes broker-only publishing impossible without a dummy `@OnOutboxEvent()` handler.

#### Design

Introduce a delivery model that separates local handler dispatch from external publishing.

Recommended public option:

```typescript
type OutboxDeliveryMode = 'local' | 'publisher';

OutboxModule.forRoot({
  prisma: PrismaService,
  delivery: {
    mode: 'publisher',
  },
  transport: KafkaOutboxTransport,
});
```

Rules:

- `local` mode:
  - default for backward compatibility;
  - event must have at least one registered handler;
  - no-handler events are marked `FAILED`, preserving 0.1.0 safety.
- `publisher` mode:
  - poller dispatches the record to transport even when no local handlers exist;
  - transport success marks event `SENT`;
  - transport failure applies retry/backoff;
  - local handler discovery is not required.

Keep the current `OutboxTransport` interface available in 0.2.0, but add a clearer publisher-oriented interface:

```typescript
export interface OutboxPublisher {
  publish(record: OutboxRecord): Promise<void>;
}
```

Compatibility adapter:

```typescript
export interface OutboxTransport {
  dispatch(record: OutboxRecord, handlers: OutboxHandler[]): Promise<void>;
}
```

Implementation can support both:

- if provider implements `publish`, use publisher path;
- otherwise use legacy `dispatch(record, handlers)`.

#### Acceptance criteria

- In `local` mode, no-handler event is marked `FAILED`.
- In `publisher` mode, no-handler event is published and then marked `SENT`.
- Legacy custom transports continue to compile.
- README custom Kafka example is updated to use the new publisher contract.

#### Tests

- Unit: `publisher` mode does not call `OutboxExplorer.getHandlers()`.
- Unit: `local` mode preserves no-handler failure.
- E2E: fake publisher receives event and row becomes `SENT`.
- E2E: fake publisher throws and row retries then fails.

### 6.2 P0 - Outbox admin and DLQ API

#### Problem

0.1.0 stores `FAILED` rows, but the only documented recovery path is manual SQL. Production users need supported operations for inspection and recovery.

#### Design

Add `OutboxAdminService` as an exported provider.

```typescript
export interface OutboxStats {
  pending: number;
  processing: number;
  sent: number;
  failed: number;
  oldestPendingAgeMs: number | null;
  oldestProcessingAgeMs: number | null;
}

export interface OutboxListOptions {
  status?: OutboxRecord['status'];
  eventType?: string;
  tenantId?: string;
  limit?: number;
  before?: Date;
  after?: Date;
}

export class OutboxAdminService {
  getStats(): Promise<OutboxStats>;
  list(options?: OutboxListOptions): Promise<OutboxRecord[]>;
  getById(id: string): Promise<OutboxRecord | null>;
  retry(id: string): Promise<boolean>;
  retryMany(ids: string[]): Promise<number>;
  markFailed(id: string, reason: string): Promise<boolean>;
  purgeSent(options: { before: Date; limit?: number }): Promise<number>;
}
```

`retry(id)` behavior:

- only `FAILED` rows are reset to `PENDING`;
- reset `last_error`;
- keep `retry_count` by default for audit;
- add an option later if users need retry count reset.

Health can be an API method, not an HTTP controller:

```typescript
getHealth(options?: {
  maxOldestPendingAgeMs?: number;
  maxFailedCount?: number;
}): Promise<{ ok: boolean; stats: OutboxStats; reasons: string[] }>;
```

#### Acceptance criteria

- Operators can list and retry failed events without SQL.
- Retrying an event never touches a currently `PROCESSING` row.
- Purge only deletes `SENT` rows older than the provided date.
- All queries use parameterized Prisma raw SQL.

#### Tests

- Unit: SQL state transitions for retry and markFailed.
- E2E: force handler failure, call admin retry, verify delivery succeeds after handler recovers.
- Unit: health result fails on pending age threshold.
- Unit: purge ignores non-SENT rows.

### 6.3 P0 - Stable event envelope and metadata

#### Problem

Current rows contain `event_type`, `payload`, `status`, retry fields, and `tenant_id`. That is enough for local handlers but weak for broker publishing, idempotency, ordering, tracing, and replay.

#### Design

Add optional metadata fields to `outbox_events`.

```sql
ALTER TABLE outbox_events
  ADD COLUMN IF NOT EXISTS aggregate_type VARCHAR(255),
  ADD COLUMN IF NOT EXISTS aggregate_id VARCHAR(255),
  ADD COLUMN IF NOT EXISTS partition_key VARCHAR(255),
  ADD COLUMN IF NOT EXISTS idempotency_key VARCHAR(255),
  ADD COLUMN IF NOT EXISTS correlation_id VARCHAR(255),
  ADD COLUMN IF NOT EXISTS causation_id VARCHAR(255),
  ADD COLUMN IF NOT EXISTS headers JSONB NOT NULL DEFAULT '{}'::jsonb,
  ADD COLUMN IF NOT EXISTS occurred_at TIMESTAMPTZ NOT NULL DEFAULT NOW();

CREATE INDEX IF NOT EXISTS idx_outbox_aggregate
  ON outbox_events (aggregate_type, aggregate_id, created_at ASC)
  WHERE aggregate_id IS NOT NULL;

CREATE INDEX IF NOT EXISTS idx_outbox_tenant_pending
  ON outbox_events (tenant_id, created_at ASC)
  WHERE status = 'PENDING' AND tenant_id IS NOT NULL;
```

Add emit options:

```typescript
export interface OutboxEmitOptions {
  tenantId?: string;
  aggregateType?: string;
  aggregateId?: string;
  partitionKey?: string;
  idempotencyKey?: string;
  correlationId?: string;
  causationId?: string;
  headers?: Record<string, string>;
  occurredAt?: Date;
}

outbox.emit(tx, new OrderCreatedEvent(order.id), {
  aggregateType: 'Order',
  aggregateId: order.id,
  partitionKey: order.id,
  correlationId: requestId,
});
```

Update `OutboxRecord`:

```typescript
export interface OutboxRecord {
  id: string;
  eventType: string;
  payload: Record<string, unknown>;
  status: 'PENDING' | 'PROCESSING' | 'SENT' | 'FAILED';
  createdAt: Date;
  updatedAt: Date;
  processedAt: Date | null;
  retryCount: number;
  maxRetries: number;
  lastError: string | null;
  tenantId: string | null;
  aggregateType: string | null;
  aggregateId: string | null;
  partitionKey: string | null;
  idempotencyKey: string | null;
  correlationId: string | null;
  causationId: string | null;
  headers: Record<string, string>;
  occurredAt: Date;
}
```

#### Acceptance criteria

- Existing `emit(tx, event)` calls keep working.
- Metadata is optional and null/defaulted when not provided.
- `headers` is always an object.
- Existing SQL migration remains valid for new installs.
- An additive v0.2 migration file is shipped for existing installs.

#### Tests

- Unit: metadata values are inserted.
- Unit: default metadata stays null or `{}`.
- E2E: metadata survives fetch/lock/dispatch.
- Type tests or compile tests for `OutboxEmitOptions`.

### 6.4 P1 - PostgreSQL LISTEN/NOTIFY wakeup

#### Problem

Polling interval adds delivery latency. The default README interval is 5000ms, which is acceptable for durability but poor for user-visible workflows such as notifications and webhooks.

#### Design

Add optional notify wakeup. It should wake the poller, not replace polling.

```typescript
OutboxModule.forRoot({
  prisma: PrismaService,
  wakeup: {
    listenNotify: {
      enabled: true,
      connectionString: process.env.DATABASE_URL,
      channel: 'outbox_events',
      reconnectDelay: 5000,
    },
  },
});
```

Add SQL migration:

```sql
CREATE OR REPLACE FUNCTION notify_outbox_events()
RETURNS trigger AS $$
BEGIN
  PERFORM pg_notify('outbox_events', NEW.id::text);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_notify_outbox_events ON outbox_events;

CREATE TRIGGER trg_notify_outbox_events
AFTER INSERT ON outbox_events
FOR EACH ROW
EXECUTE FUNCTION notify_outbox_events();
```

Implementation rules:

- `NOTIFY` triggers `poll()` soon.
- Polling interval still runs as fallback.
- Listener reconnects after connection failure.
- Listener is disabled by default to avoid adding a required `pg` dependency unless the dependency strategy is decided.

Dependency strategy options:

1. Use optional peer dependency `pg`.
2. Provide a small subpath package later.
3. Use Prisma only and skip LISTEN/NOTIFY in 0.2.0.

Recommended for 0.2.0: optional peer dependency `pg` only when `listenNotify.enabled` is true.

#### Acceptance criteria

- Inserted outbox row wakes poller before the next interval.
- If notification is missed, normal polling still processes the row.
- Shutdown closes listener connection.
- Connection error logs warning and reconnects.

#### Tests

- E2E: notify path processes event without waiting full interval.
- E2E: disabled notify behaves like 0.1 polling.
- Unit: reconnect backoff scheduling.
- Benchmark: compare polling-only and notify-enabled latency.

### 6.5 P1 - Tenancy propagation

#### Problem

`tenant_id` exists but is not populated. Multi-tenant SaaS users need tenant-aware filtering, replay, and downstream context.

#### Design

Add optional tenancy integration that does not require `@nestarc/tenancy` as a hard dependency.

```typescript
export interface OutboxTenantProvider {
  getTenantId(): string | null | undefined;
  runWithTenant?<T>(tenantId: string, fn: () => Promise<T>): Promise<T>;
}

OutboxModule.forRoot({
  prisma: PrismaService,
  tenancy: {
    provider: NestarcTenancyProvider,
  },
});
```

Emitter behavior:

1. `emit(..., { tenantId })` wins if provided.
2. tenancy provider value is used if available.
3. otherwise `tenant_id` is null.

Local handler behavior:

- If record has `tenantId` and provider has `runWithTenant`, execute handler inside tenant context.
- If provider is missing, pass tenant id only in `OutboxRecord`.

#### Acceptance criteria

- No hard dependency on `@nestarc/tenancy`.
- Explicit `tenantId` override works.
- Provider-based tenant id is stored.
- Handler context restoration works when provider supports it.

#### Tests

- Unit: explicit tenant id.
- Unit: provider tenant id.
- Unit: explicit id overrides provider id.
- Unit/E2E: local handler receives restored tenant context.

### 6.6 P1 - Observability hooks

#### Problem

Async delivery failures are hard to diagnose from the outside. Users need metrics and tracing, but core should avoid a heavy required dependency.

#### Design

Add lifecycle hooks as plain callbacks.

```typescript
export interface OutboxHooks {
  onEmit?(context: OutboxEmitContext): void | Promise<void>;
  onPollStart?(context: OutboxPollContext): void | Promise<void>;
  onDispatchStart?(context: OutboxDispatchContext): void | Promise<void>;
  onDispatchSuccess?(context: OutboxDispatchContext & { durationMs: number }): void | Promise<void>;
  onDispatchFailure?(context: OutboxDispatchContext & { error: Error; durationMs: number }): void | Promise<void>;
  onRetryScheduled?(context: OutboxRetryContext): void | Promise<void>;
  onDeadLetter?(context: OutboxRetryContext): void | Promise<void>;
}
```

Hook failure rules:

- hook failures must not change event delivery state;
- hook errors are logged and swallowed by default;
- a future option may allow strict hook failure behavior.

#### Acceptance criteria

- Users can record backlog, duration, success, and failure metrics.
- Hook errors do not mark events failed.
- Hooks receive event id, type, tenant id, retry count, and metadata.

#### Tests

- Unit: hook call order.
- Unit: hook exceptions are isolated.
- Unit: failure and retry hooks receive correct retry count.

### 6.7 P2 - Bulk `emitMany()` optimization

#### Problem

`emitMany()` currently loops and performs one insert per event. The v0.1 design doc claimed a single multi-row insert, and a benchmark already exists.

#### Design

Implement a safe batch insert path for PostgreSQL.

Options:

- Use `Prisma.sql` helpers if the package can import Prisma runtime types safely.
- Keep loop in 0.2.0 if safe dynamic raw SQL would compromise type safety.

Recommended: implement only if the SQL can remain parameterized and maintainable. Otherwise document current behavior and leave optimization to 0.3.

#### Acceptance criteria

- `emitMany([])` remains a no-op.
- `emitMany([a, b])` inserts all rows in the same transaction.
- If batch insert fails, transaction rollback removes all event rows.
- No unsafe string interpolation for payload values.

#### Tests

- Unit: single raw call if optimized.
- E2E: rollback removes all batch events.
- Benchmark: compare 0.1 loop with 0.2 implementation.

## 9. Internal Architecture

### 9.1 Minimal refactor recommended for 0.2.0

Do not rewrite the package. Extract only the pieces required to keep 0.2 changes controlled.

Recommended new internal services:

```text
src/outbox.repository.ts
src/outbox.admin.service.ts
src/outbox.delivery.ts
src/outbox.listener.ts          optional LISTEN/NOTIFY
src/outbox.hooks.ts
```

Responsibilities:

- `OutboxRepository`: raw SQL for insert, fetch/lock, mark sent, mark failed, retry, stats.
- `OutboxDelivery`: chooses local vs publisher path.
- `OutboxAdminService`: public operations backed by repository.
- `OutboxListener`: optional Postgres notifications.
- `OutboxPoller`: scheduling and lifecycle orchestration only.

### 9.2 Avoid over-refactoring

Do not introduce a large domain layer or generic queue abstraction. 0.2.0 should reduce `OutboxPoller` coupling only where new features require it.

## 10. Delivery Semantics

### 10.1 Guarantees

`@nestarc/outbox` should document these guarantees:

- If business DB transaction rolls back, the outbox event is not stored.
- If business DB transaction commits, the event is durably stored.
- Polling delivery is at-least-once.
- `FOR UPDATE SKIP LOCKED` prevents concurrent processing of the same row by multiple pollers.
- Broker publishing can still duplicate if the process crashes after broker ack but before marking the row `SENT`.

### 10.2 Non-guarantees

The package does not guarantee:

- exactly-once broker delivery;
- exactly-once consumer side effects;
- global event ordering;
- aggregate-level ordering in 0.2.0 unless explicitly added;
- delivery if users bypass `outbox.emit(tx, event)` after changing business data.

### 10.3 Required guidance

README must explicitly recommend idempotent consumers. Use `record.id` or `idempotencyKey` as the consumer dedupe key.

## 14. Risks

### 14.1 Public API risk

Changing transport semantics can break custom transports. Mitigation: keep legacy `dispatch(record, handlers)` for 0.2.0 and add publisher mode alongside it.

### 14.2 Duplicate delivery risk

At-least-once delivery means duplicates remain possible. Mitigation: document this clearly and expose event ids/idempotency keys.

### 14.3 LISTEN/NOTIFY risk

Notifications are not a durable queue. Mitigation: use it only as a wakeup signal and keep polling fallback.

### 14.4 Migration risk

Metadata columns are additive, but new code may assume their existence. Mitigation: ship upgrade migration and fail clearly if required columns are missing.

### 14.5 Scope risk

Combining broker mode, admin API, metadata, wakeup, tenancy, and observability is substantial. If schedule tightens, keep P0 items and defer LISTEN/NOTIFY or tenancy.

## 15. Open Questions

1. Should `pg` become an optional peer dependency for LISTEN/NOTIFY, or should wakeup be deferred to avoid dependency growth?
2. Should `retry(id)` preserve `retry_count` or reset it by default?
3. Should metadata columns include `schema_version` now, or wait until event validation/schema support exists?
4. Should `OutboxPublisher` be a new public export in 0.2.0, or should the package keep only one transport interface and change its shape in a future major?
5. Should `tenant_id` be an explicit emit option only, or should `@nestarc/tenancy` integration ship in 0.2.0?
6. Should strict per-aggregate ordering be explicitly deferred to 0.3.0?
